# FORK.md: T3 Code + lastdrop

Read this before resolving an upstream conflict or touching a T3 file.

This repository is a fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code). The `lastdrop` branch is the fork's commits with each stable upstream tag (`vX.Y.Z`) merged in; its diff from the newest merged tag is the whole fork. The fork adds lastdrop (several Claude accounts picked by remaining limits, the user's own agents with fallbacks across providers) and installs as its own app that opens the official T3 Code's data (`~/.t3`). Use one of the two apps at a time.

## Rules

1. **Share as little code with T3 as possible.** Fork code lives only in the fork's folders (below). T3 files change only at the seams listed here, a few lines each, and never in large files such as `ClaudeAdapterV2.ts` or `OrchestratorMcpService.ts`.
2. **The guard enforces it.** `node scripts/lastdrop/check-fork-paths.ts` compares `HEAD` with the upstream tag it is based on and fails on any changed path outside the fork's folders, or on a seam whose changed lines (added + deleted) exceed its budget in `scripts/lastdrop/seams.json`. It runs in CI and before every local push (`.vite-hooks/pre-push`, skipped in CI). `pnpm-lock.yaml` is exempt (regenerate it, never hand-merge it).
3. **A new seam needs an entry in `seams.json` and a section here**, in the same PR. A change to a seam updates its section.
4. **Upstream tests stay untouched and green.** Where the fork changes behaviour that T3's tests pin (the app identity), the change is switched on at runtime by the fork's entry point, not by editing T3's defaults or tests.
5. **The README changes only in its top section, and keeps it current.** Fork changes to `README.md` go only in the "T3 Code + lastdrop" section above upstream's README (on a conflict, take upstream's README and put the section back on top). When a change adds something users notice, update its "What it adds" list in the same PR. Keep it concise, impactful and simple: what the user gets, not how it works.

## Seams

Line numbers are at v0.1.9 and drift; find each seam by the code it sits beside. "Must survive" is what a merge must keep. With every extension list empty the app behaves exactly as upstream, so if a seam is lost, the app still runs but the fork's features silently disappear: check each seam after every sync.

## App identity and data

The fork is its own app that opens the official app's data: the same T3 home (`~/.t3`, or `T3CODE_HOME`, resolved by T3's own code; dev runs: `~/.t3/dev`), database, settings and secrets. Everything the fork adds goes under its own folder or files, never into T3's files or schema.

|                            | Official T3 Code                          | Fork                                                 |
| -------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| App / bundle id            | `T3 Code (Beta)` / `com.t3tools.t3code`   | `T3 Code lastdrop` / `com.amontlabs.t3code-lastdrop` |
| T3 home (`T3CODE_HOME`)    | `~/.t3`                                   | same                                                 |
| lastdrop's own files       |                                           | `~/.t3/lastdrop/` (dev runs: `~/.t3/dev/lastdrop/`)  |
| Electron profile           | `~/Library/Application Support/t3code-v2` | `~/Library/Application Support/t3code-lastdrop`      |
| `t3` command shim          | `~/.t3/bin/t3`                            | `~/.t3/lastdrop/bin/t3`; never writes `~/.t3/bin/t3` |
| Safe-storage keychain item | `t3code Safe Storage`                     | same                                                 |
| Updater cache              | `~/Library/Caches/t3code-updater`         | same                                                 |
| `t3code://` links          | registered                                | registered                                           |
| Updates                    | pingdotgg/t3code releases                 | amontlabs/t3code releases                            |

How: `apps/desktop/src/extensions/startup.ts` runs first and calls `Identity.activate()`: the app-name and profile seams then return the fork's names (until then they return T3's, which is what T3's tests see). It does not touch `T3CODE_HOME`. lastdrop's folder comes from `lastdropDataDir` / `resolveLastdropDataDir` in `apps/server/src/extensions/dataDir.ts`, derived from the server's resolved home; nothing creates it yet.

Nothing in `~/.t3` depends on the bundle id; the id keeps macOS preferences, privacy permissions and the updater apart.

### Shared data with the official app

- **Keychain**: the staged package name stays `t3code`, so Electron reads the official app's `t3code Safe Storage` key and decrypts its saved environments and connection catalog. The fork's signature differs, so macOS asks once for access to that item ("Always Allow").
- **One app at a time**: each app has its own Electron profile and single-instance lock, so both can be opened. T3's server takes an exclusive lock on `~/.t3/userdata/server-owner.sqlite` before it opens the database (`apps/server/src/serverOwnership.ts`). The second app's server exits with code 78, and that app shows T3's "This T3 home is unavailable" dialog and quits. Two servers never run on one home. Before its server exits, the second app may already have rewritten the `t3` command shim to point at itself.
- **Newer schema**: the official app can update ahead of the fork and migrate the database. T3's migrator then runs nothing on the newer schema, and T3 refuses that only for its background service. The fork checks right after the ownership lock (`databaseVersion.ts`, read-only): if the database records migrations this build does not know, the server stops before opening it, nothing is written, and the startup-recovery window shows the message and offers the fork's update. The fork follows stable T3 releases within the hour, so this lasts until the next fork release. The fork never adds migrations of its own.
- **Sign-in links**: both apps register `t3code://` (Clerk and Codex sign-in callbacks), and macOS sends a link to only one of them. Keep only one of the two installed.
- **Updater cache**: shared. Each app checks a cached download against its own update's hash, so neither installs the other's update; at worst one deletes the other's pending download and it downloads again.
- **Other shared state**: scheduled tasks, worktrees, the environment id and the server's runtime files are T3's own and belong to whichever app is running. Electron-profile state (window layout, Chromium storage) is per app.

### The standalone lastdrop app

Nothing is shared with it: the fork never reads, writes or runs the app's folder, account folders, keychain items or binary, and works with the app absent. The only readers are the one-time "Import from the lastdrop app" buttons (`appImport.ts`, `catalogEdit.ts`, `importFromApp.ts`), which copy and never write. The vendored plugin, unchanged, can still fall back to the app's runner when the fork's fails. Claude Code's and Codex's own terminal logins are used only while no fork account is signed in (docs/lastdrop/independence.md).

**Data the fork stores**: its own files under `~/.t3/lastdrop/`, later also settings in provider instance `config`.

- `accounts.json`: the Claude accounts in priority order and the routing thresholds (the standalone lastdrop's `accounts.json` format); `accounts/<key>/`: each account's sign-in folder and profile (Main's too).
- `usage.json`: each Claude account's latest reading, rate-limit block and sign-in state (the standalone lastdrop's `usage.json` format, dates in seconds).
- `lastdrop.log`: one line per renewal, refused request or sign-in that needs the user, and per approval request lastdrop answered for an agent thread.
- `helper/`: an empty folder `claude` starts in when renewing a sign-in or signing in.
- `agent-threads.json`: which agent entry (and instance) made each native thread, so a restart resumes a thread only on its own instance.
- `agent-room.json`: agent entries out at a usage limit, until when.
- `sessions.json`: the session ledger: each Claude conversation's account (and for a fork, when and from which), the conversation each T3 native session continues in now (the old → new id map after a move), and each T3 thread's last account. Lines of `lastdrop.log` say where each query opened and why.
- `bin/lastdrop`: the runner script lastdrop's plugin runs in fork threads, rewritten at each server start (it holds no secret: the address and the thread's token come in each query's environment).
- `agent-runs.json`: each run the plugin started through the runner (Claude Code's agent id → parent thread, child thread, agent), for follow-ups after a restart.
- `endpoint-instances.json`: which provider instance ids lastdrop made (claimed on disk before T3's `create`), and the user's switch and colour on one lastdrop removed, put back if it is made again.
- `endpoints/<provider>/`: the Z.ai/OpenRouter Claude Code profiles (key helper settings, onboarding, links into `~/.claude`); `endpoints/key-helper` prints the key from the keychain at launch.
- Keychain: the Z.ai and OpenRouter API keys are items `zai-api-key` and `openrouter-api-key` of service `t3code-lastdrop` (base64, written with `security -i`, never in an argument list), set from Settings → Providers → Claude (the main card's "Z.ai and OpenRouter keys", then each provider's own card) through `/api/lastdrop/endpoints/keys` (`endpointKeys.ts`; changing a key needs a local session with `orchestration:operate`, a remote DPoP session is refused). `endpoint-keys-import.json` marks the one-time "Import from the lastdrop app" as done.
- `plugin/lastdrop/`: lastdrop's Claude Code plugin, rewritten from the copy embedded in the server at each start (`pluginFiles.generated.ts`, rebuilt by `scripts/lastdrop/sync-plugin.sh`; `plugin.test.ts` fails while it lags `packages/lastdrop-plugin`). It sits under the data folder so no packaging step, and no seam, is needed: dev, the server bundle and the desktop app all resolve it as `<T3 home>/lastdrop/plugin/lastdrop`.
- T3's own `settings.json` gets `providerInstances.lastdropAgents: { driver, enabled: true }` whenever it has no such entry (at start, and after "Reset to defaults") (`agents/defaultOn.ts`), so "lastdrop agents" is on in a fresh home as its switch shows. It is the entry the switch writes, and an existing entry is never changed. The official app shows it as an unknown driver, read-only.
- T3's own `settings.json` gets the `zai`/`openrouter` instances through `ServerSettingsService.updateProviderInstance` (labelled `Z.ai` and `OpenRouter`, no key in them, the endpoint env inline in `--settings`). Each carries the marker `LASTDROP_ENDPOINT=<provider>` in its environment and `lastdropEndpoint` in its config; lastdrop changes only marked instances whose id it recorded, and only its own fields of them.

### Rules other fork code must keep

- **The runner's variables (step 8) and the plugin are the only things added to a Z.ai or OpenRouter query**: `LASTDROP_RUNNER`, `LASTDROP_RUNNER_URL`, `LASTDROP_RUNNER_TOKEN`, and the SDK's `plugins: [{ type: "local", path }]` with `enabledPlugins["lastdrop@lastdrop"] = false` in the query's flag settings, so the app's installed copy never shows beside it (`runner/queryEnvironment.ts`, outside the routing wrapper). They pick no account and change no endpoint.
- **The query-runner wrapper (step 4) never touches a Z.ai or OpenRouter query.** Before picking a Claude account, setting `CLAUDE_SECURESTORAGE_CONFIG_DIR`/`CLAUDE_CONFIG_DIR` or moving a thread, it calls `isLastdropEndpointEnvironment(env)` (or `isLastdropEndpointInstance(instance)`, both from `@t3tools/lastdrop-node`) and passes the query through unchanged when it holds. Pinned by `endpoints.test.ts` on the process env T3 builds from the instance.

### These instances in the official app, and uninstalling

The official app reads the same `settings.json`, so it shows and runs lastdrop's `zai` and `openrouter` instances too: they work there while `~/.t3/lastdrop/endpoints/` exists (Claude Code needs the profile and its key helper), but nothing updates them. If that folder is deleted, every thread on them fails at launch with Claude Code's `apiKeyHelper` error. The official app can't tell the fork is gone, so nothing disables them automatically. To uninstall: remove lastdrop's `Z.ai` and `OpenRouter` in Settings → Providers first (or delete the `zai` and `openrouter` entries of `providerInstances` in `~/.t3/userdata/settings.json` with both apps closed), then `~/.t3/lastdrop/`.

**Data the fork stores** (agents): `~/.t3/lastdrop/agents.json` is the user's agents (name, description, provider, model, effort, ordered fallbacks, enabled), in the standalone app's `agent-catalog.json` format, so `parseCatalog` and the Claude Code plugin read it unchanged. A save rewrites the whole file through a temporary file, bumps its `revision`, and keeps every key the editor does not know (`judges`, `saveClaude`, an agent's extras). `agent-models.json` beside it is the efforts cache (`{provider: {models: [{id, efforts}]}}`), only read; without it the editor and the driver fall back to each model's own published efforts or the provider's caller levels. Both are polled every 2 s, so a hand edit applies without a restart. A missing `agents.json` is an empty list, not a warning. **The one-time import**: while the fork has no agents and the app's `~/Library/Application Support/lastdrop/agent-catalog.json` has some, Settings offers "Import from the lastdrop app", which copies that file (and `agent-models.json` when the fork has none) into `~/.t3/lastdrop/`. The app's files are only read by that button (`appCatalogFiles` in `catalogEdit.ts` is the one place that names its folder) and never written.

**Claude accounts** are the fork's own (docs/lastdrop/independence.md, item 1), every one of them, Main included: the list `~/.t3/lastdrop/accounts.json` (the app's format), each account's sign-in folder `~/.t3/lastdrop/accounts/<key>` with its profile in `profile/` (links into `~/.claude` for settings, skills, agents and conversations, and a `.claude.json` rebuilt from `~/.claude.json`) and its own Claude Code keychain item (named after the folder). Claude Code's own login (`~/.claude`, keychain item `Claude Code-credentials`) is never read, renewed or routed to while a fork account can take work, so `claude /login` or `/logout` in a terminal changes nothing in the fork. With no fork account signed in (a fresh install), Claude threads run on that login and the section says so ("Using Claude Code's own login"). An older list's `main` (from when Main meant that login) keeps its key and gets its own folder, signed out until it is signed in from the section; nothing is copied from `~/.claude` (its rotating refresh token would invalidate the terminal's). Settings → Providers → Claude → Accounts adds, signs in (`claude auth login` in the folder, the page's code pasted in the section), renames, reorders and removes any account (deleting only that folder and its keychain item). While the fork has no accounts (or only an older list's `main`) and the app lists some, "Import from the lastdrop app" copies their names and order once (`appImport.ts`, the only reader of the app's `accounts.json`); each then signs in again. Renewing a sign-in starts `claude -p` in the account's folder. The service runs only on macOS, and not under vitest (T3's own server tests start the layer). The fork always reads usage and renews sign-ins itself, whether or not the app runs.

## Releases

- **Versions**: `v<upstream>-ld.<n>`, for example `v0.1.10-ld.1`, then `-ld.2` for a fork-only release on the same base. Semver orders them after the upstream version, and electron-updater compares plain semver, so updates flow across bases.
- **Update feed**: the build writes `app-update.yml` for `T3CODE_DESKTOP_UPDATE_REPOSITORY` (`amontlabs/t3code`). The app reads the stable channel: GitHub's latest full release and its `latest-mac.yml`. Releases must not be marked prerelease.
- **Release signing**: a self-signed code-signing certificate, the same one forever, in secrets `LASTDROP_SIGNING_CERT_P12` (base64 `.p12`) and `LASTDROP_SIGNING_CERT_PASSWORD`. Squirrel.Mac installs an update only if it satisfies the running app's designated requirement; ad-hoc signing makes that the code hash, so every update would fail, while a fixed certificate makes it `certificate leaf = H"<sha1>"`. No notarization: the first install is opened once through System Settings → Privacy & Security. `lastdrop-release.yml` imports the certificate into a temporary keychain added to the search list (codesign finds an untrusted self-signed identity only there), and the build signs through `scripts/lastdrop/sign-macos.ts` (electron-builder is told `identity: "-"` so it skips its Apple-only certificate lookup). Releases are never published unsigned. To make the certificate: Keychain Access → Certificate Assistant → Create a Certificate, type "Code Signing", self-signed root; export it as `.p12`. Verify a two-version update before relying on it.

## Sync

`.github/workflows/lastdrop-sync.yml`, hourly (GitHub runs schedules late, often hours apart) and on manual dispatch (both use the copy of the workflow on the repository's default branch):

1. Turns off every workflow that is not `lastdrop-*` (upstream's would fail or wait for upstream's runners).
2. Finds the newest stable upstream tag (`^v\d+\.\d+\.\d+$`; nightly and preview tags are skipped). Nothing newer than the base of `lastdrop`, or `lastdrop-sync/<tag>` already exists (waiting for a person): done.
3. `git merge <tag>`. Only files both sides changed since the last sync can conflict, which is the seams (fork folders are the fork's alone). The lockfile takes upstream's; any other conflict goes to Claude Code, headless, which reads this file in full, then resolves the conflicted files (`sync-resolve.md`, Sonnet). If it stops, the conflict goes to a PR (step 7).
4. Regenerates `pnpm-lock.yaml` (`vp install --lockfile-only`), installs, then `scripts/lastdrop/sync-checks.sh`: the guard, each package's typecheck and tests one package at a time (`vp run` stops starting tasks after a failure, and the standard runner runs out of memory with several typechecks at once), `vp run build:desktop`. A package whose run crashed (killed for memory, test browser gone) runs once more; a real failure does not.
5. Red: Claude gets one attempt at a fix (`sync-fix.md`, Opus, inside the fork's folders and seams only), starting from a digest of the failures rather than the whole log, then the checks run again.
6. Green: moves `lastdrop` (only if nobody pushed meanwhile), deletes every `lastdrop-sync/*` branch (closing older stuck syncs' PRs), and pushes tag `v<tag>-ld.<n>`, which runs `lastdrop-release.yml`.
7. Still stuck: pushes `lastdrop-sync/<tag>` (the upstream tag on a conflict, the merged branch on red checks) with a PR into `lastdrop`, labelled `lastdrop-sync`, carrying Claude's notes and the log. The hourly job does not retry while that branch exists.

The gate is the checks, not Claude: a sync Claude resolved or fixed ships like a clean one, and its changes are visible in the merge commit and any `lastdrop: sync fixes` or `lastdrop: fixes for <tag>` commit. Each Claude step is capped (`--max-budget-usd`) and the run summary lists its turns, tokens and cost at API prices. The app's sidebar shows a warning while a PR labelled `lastdrop-sync` is open or the latest finished `lastdrop-release.yml` run failed, linking to it (`apps/web/src/extensions/lastdrop/SyncNotice.tsx`, GitHub's public API; issues are off on this repository).

`lastdrop-guard.yml` runs the guard on every push and PR to `lastdrop`. A person can release by pushing a `v*-ld.*` tag.

**Dry run**: dispatch with `dry_run` and any upstream ref as `tag` (such as `main`) to run steps 3 to 5 against it. It pushes, opens and releases nothing; the outcome and Claude's notes are in the run summary.

**Repository setup**:

- Secret `LASTDROP_SYNC_TOKEN`: a fine-grained token for this repository only, with Contents and Workflows read and write. The workflow token cannot push commits that change `.github/workflows/`, which upstream's releases do, and a tag it pushes starts no workflow.
- Secrets `CLAUDE_CODE_OAUTH_TOKEN` and, optionally, `CLAUDE_CODE_OAUTH_TOKEN_2`: from `claude setup-token`, each on a Claude subscription. The second is used when the first account is at its limit. They last a year.
- Actions settings: "Allow GitHub Actions to create and approve pull requests", so the workflow token opens the PRs (and you are notified of them, which you would not be for a PR opened as you).

### Resolving a sync

1. `git fetch origin && git fetch https://github.com/pingdotgg/t3code.git 'refs/tags/<tag>:refs/tags/<tag>'`.
2. `git switch lastdrop && git merge <tag>` (or start from `lastdrop-sync/<tag>` when checks were red).
3. For each conflict (`--ours` is the fork, `--theirs` upstream; `git diff <previous> lastdrop -- <file>` is the fork's change to a file):
   - a seam: start from upstream's file and re-apply the seam from its section above;
   - `pnpm-lock.yaml`: take upstream's, then `vp install --lockfile-only` at the end;
   - any other upstream file: it should not differ from upstream, take upstream's;
   - a file in a fork folder: upstream should never touch these paths, so this means upstream now uses the same path for something of its own. Neither side can be dropped: move the fork's file to a path upstream does not use, update its imports and this file, then take upstream's.
4. `node scripts/lastdrop/check-fork-paths.ts`, then the checks for the packages you touched (`vp run check:changed`) and the desktop tests.
5. `git push origin lastdrop`, then push tag `v<tag>-ld.1` to release. Close the PR and delete `lastdrop-sync/<tag>`.
