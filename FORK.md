# FORK.md: T3 Code + lastdrop

Read this before resolving an upstream conflict or touching a T3 file.

This repository is a fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code). The `lastdrop` branch is the latest stable upstream tag (`vX.Y.Z`) plus a short stack of fork commits on top. The fork adds lastdrop (several Claude accounts picked by remaining limits, the user's own agents with fallbacks across providers) and installs as its own app that opens the official T3 Code's data (`~/.t3`). Use one of the two apps at a time.

## Rules

1. **Share as little code with T3 as possible.** Fork code lives only in the fork's folders (below). T3 files change only at the seams listed here, a few lines each, and never in large files such as `ClaudeAdapterV2.ts` or `OrchestratorMcpService.ts`.
2. **The guard enforces it.** `node scripts/lastdrop/check-fork-paths.ts` compares `HEAD` with the upstream tag it is based on and fails on any changed path outside the fork's folders, or on a seam whose changed lines (added + deleted) exceed its budget in `scripts/lastdrop/seams.json`. `pnpm-lock.yaml` is exempt (regenerate it, never hand-merge it).
3. **A new seam needs an entry in `seams.json` and a section here**, in the same PR. A change to a seam updates its section.
4. **Upstream tests stay untouched and green.** Where the fork changes behaviour that T3's tests pin (the app identity), the change is switched on at runtime by the fork's entry point, not by editing T3's defaults or tests.

## App identity and data

The fork is its own app that opens the official app's data: the same T3 home (`~/.t3`, or `T3CODE_HOME`, resolved by T3's own code; dev runs: `~/.t3/dev`), database, settings and secrets. Everything the fork adds goes under its own folder or files, never into T3's files or schema.

|                            | Official T3 Code                          | Fork                                                 |
| -------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| App / bundle id            | `T3 Code (Beta)` / `com.t3tools.t3code`   | `T3 Code lastdrop` / `com.amontlabs.t3code-lastdrop` |
| T3 home (`T3CODE_HOME`)    | `~/.t3`                                   | same                                                 |
| lastdrop's own files       |                                           | `~/.t3/lastdrop/` (dev runs: `~/.t3/dev/lastdrop/`)  |
| Electron profile           | `~/Library/Application Support/t3code-v2` | `~/Library/Application Support/t3code-lastdrop`      |
| `t3` command shim          | `~/.t3/bin/t3`                            | `~/.t3/lastdrop/bin/t3`; never writes `~/.t3/bin/t3` |
| Safe-storage keychain item | `t3code Safe Storage`                     | same                                                 |
| Updater cache              | `~/Library/Caches/t3code-updater`         | same                                                 |
| `t3code://` links          | registered                                | registered                                           |
| Updates                    | pingdotgg/t3code releases                 | amontlabs/t3code releases                            |

How: `apps/desktop/src/extensions/startup.ts` runs first and calls `Identity.activate()`: the app-name and profile seams then return the fork's names (until then they return T3's, which is what T3's tests see). It does not touch `T3CODE_HOME`. lastdrop's folder comes from `lastdropDataDir` / `resolveLastdropDataDir` in `apps/server/src/extensions/dataDir.ts`, derived from the server's resolved home; nothing creates it yet.

Nothing in `~/.t3` depends on the bundle id; the id keeps macOS preferences, privacy permissions and the updater apart.

### Shared data with the official app

- **Keychain**: the staged package name stays `t3code`, so Electron reads the official app's `t3code Safe Storage` key and decrypts its saved environments and connection catalog. The fork's signature differs, so macOS asks once for access to that item ("Always Allow").
- **One app at a time**: each app has its own Electron profile and single-instance lock, so both can be opened. T3's server takes an exclusive lock on `~/.t3/userdata/server-owner.sqlite` before it opens the database (`apps/server/src/serverOwnership.ts`). The second app's server exits with code 78, and that app shows T3's "This T3 home is unavailable" dialog and quits. Two servers never run on one home. Before its server exits, the second app may already have rewritten the `t3` command shim to point at itself.
- **Newer schema**: the official app can update ahead of the fork and migrate the database. T3's migrator then runs nothing on the newer schema, and T3 refuses that only for its background service. The fork checks right after the ownership lock (`databaseVersion.ts`, read-only): if the database records migrations this build does not know, the server stops before opening it, nothing is written, and the startup-recovery window shows the message and offers the fork's update. The fork follows stable T3 releases within the hour, so this lasts until the next fork release. The fork never adds migrations of its own.
- **Sign-in links**: both apps register `t3code://` (Clerk and Codex sign-in callbacks), and macOS sends a link to only one of them. Keep only one of the two installed.
- **Updater cache**: shared. Each app checks a cached download against its own update's hash, so neither installs the other's update; at worst one deletes the other's pending download and it downloads again.
- **Other shared state**: scheduled tasks, worktrees, the environment id and the server's runtime files are T3's own and belong to whichever app is running. Electron-profile state (window layout, Chromium storage) is per app.

**Data the fork stores**: its own files under `~/.t3/lastdrop/`, later also settings in provider instance `config`.

- `usage.json`: each Claude account's latest reading, rate-limit block and sign-in state (the standalone lastdrop's `usage.json` format, dates in seconds).
- `lastdrop.log`: one line per renewal, refused request or sign-in that needs the user, and per approval request lastdrop answered for an agent thread.
- `helper/`: an empty folder `claude` starts in when renewing a sign-in.
- `agent-threads.json`: which agent entry (and instance) made each native thread, so a restart resumes a thread only on its own instance.
- `agent-room.json`: agent entries out at a usage limit, until when.
- `sessions.json`: the session ledger: each Claude conversation's account (and for a fork, when and from which), the conversation each T3 native session continues in now (the old → new id map after a move), and each T3 thread's last account. Lines of `lastdrop.log` say where each query opened and why.
- `bin/lastdrop`: the runner script lastdrop's plugin runs in fork threads, rewritten at each server start (it holds no secret: the address and the thread's token come in each query's environment).
- `agent-runs.json`: each run the plugin started through the runner (Claude Code's agent id → parent thread, child thread, agent), for follow-ups after a restart.
- `endpoint-instances.json`: which provider instance ids lastdrop made (claimed on disk before T3's `create`), and the user's switch and colour on one lastdrop removed, put back if it is made again.
- `endpoints/<provider>/`: the Z.ai/OpenRouter Claude Code profiles (key helper settings, onboarding, links into `~/.claude`); `endpoints/key-helper` prints the key from the keychain at launch.
- T3's own `settings.json` gets `providerInstances.lastdropAgents: { driver, enabled: true }` whenever it has no such entry (at start, and after "Reset to defaults") (`agents/defaultOn.ts`), so "lastdrop agents" is on in a fresh home as its switch shows. It is the entry the switch writes, and an existing entry is never changed. The official app shows it as an unknown driver, read-only.
- T3's own `settings.json` gets the `zai`/`openrouter` instances through `ServerSettingsService.updateProviderInstance` (labelled `(lastdrop)`, no key in them, the endpoint env inline in `--settings`). Each carries the marker `LASTDROP_ENDPOINT=<provider>` in its environment and `lastdropEndpoint` in its config; lastdrop changes only marked instances whose id it recorded, and only its own fields of them.

### Rules other fork code must keep

- **The runner's variables (step 8) are the only thing added to a Z.ai or OpenRouter query**: `LASTDROP_RUNNER`, `LASTDROP_RUNNER_URL`, `LASTDROP_RUNNER_TOKEN` (`runner/queryEnvironment.ts`, outside the routing wrapper). They pick no account and change no endpoint.
- **The query-runner wrapper (step 4) never touches a Z.ai or OpenRouter query.** Before picking a Claude account, setting `CLAUDE_SECURESTORAGE_CONFIG_DIR`/`CLAUDE_CONFIG_DIR` or moving a thread, it calls `isLastdropEndpointEnvironment(env)` (or `isLastdropEndpointInstance(instance)`, both from `@t3tools/lastdrop-node`) and passes the query through unchanged when it holds. Pinned by `endpoints.test.ts` on the process env T3 builds from the instance.

### These instances in the official app, and uninstalling

The official app reads the same `settings.json`, so it shows and runs the `(lastdrop)` instances too: they work there while `~/.t3/lastdrop/endpoints/` exists (Claude Code needs the profile and its key helper), but nothing updates them. If that folder is deleted, every thread on them fails at launch with Claude Code's `apiKeyHelper` error. The official app can't tell the fork is gone, so nothing disables them automatically. To uninstall: remove `Z.ai (lastdrop)` and `OpenRouter (lastdrop)` in Settings → Providers first (or delete the `zai` and `openrouter` entries of `providerInstances` in `~/.t3/userdata/settings.json` with both apps closed), then `~/.t3/lastdrop/`.

**Data the fork reads and shares with the standalone lastdrop** (never rewritten by the fork): the agent catalog `agent-catalog.json` and the agents' model efforts `agent-models.json` (same folder, polled every 2 s); the account list `~/Library/Application Support/lastdrop/accounts.json` (or the older `claude-accounts.json`), each account's sign-in folder `~/.claude-accounts/<key>` and its Claude Code keychain item. The fork does write each account's profile, `~/.claude-accounts/<key>/profile/` (links into `~/.claude` and a `.claude.json` rebuilt from Main's), exactly as the standalone app does before a run; renewing a sign-in starts `claude -p` in the account's folder, which renews its keychain item. The service runs only on macOS, and not under vitest (T3's own server tests start the layer). While the standalone app runs (its `app.heartbeat` under a minute old), the fork reads its `usage.json` instead of asking Anthropic or renewing sign-ins itself.

## Releases

- **Versions**: `v<upstream>-ld.<n>`, for example `v0.1.10-ld.1`, then `-ld.2` for a fork-only release on the same base. Semver orders them after the upstream version, and electron-updater compares plain semver, so updates flow across bases.
- **Update feed**: the build writes `app-update.yml` for `T3CODE_DESKTOP_UPDATE_REPOSITORY` (`amontlabs/t3code`). The app reads the stable channel: GitHub's latest full release and its `latest-mac.yml`. Releases must not be marked prerelease.
- **Release signing**: a self-signed code-signing certificate, the same one forever, in secrets `LASTDROP_SIGNING_CERT_P12` (base64 `.p12`) and `LASTDROP_SIGNING_CERT_PASSWORD`. Squirrel.Mac installs an update only if it satisfies the running app's designated requirement; ad-hoc signing makes that the code hash, so every update would fail, while a fixed certificate makes it `certificate leaf = H"<sha1>"`. No notarization: the first install is opened once through System Settings → Privacy & Security. `lastdrop-release.yml` imports the certificate into a temporary keychain added to the search list (codesign finds an untrusted self-signed identity only there), and the build signs through `scripts/lastdrop/sign-macos.ts` (electron-builder is told `identity: "-"` so it skips its Apple-only certificate lookup). Releases are never published unsigned. To make the certificate: Keychain Access → Certificate Assistant → Create a Certificate, type "Code Signing", self-signed root; export it as `.p12`. Verify a two-version update before relying on it.

## Sync

`.github/workflows/lastdrop-sync.yml`, hourly and on manual dispatch (both use the copy of the workflow on the repository's default branch):

1. Turns off every workflow that is not `lastdrop-*` (upstream's would fail or wait for upstream's runners).
2. Finds the newest stable upstream tag (`^v\d+\.\d+\.\d+$`; nightly and preview tags are skipped). Nothing newer than the base of `lastdrop`: done.
3. `git rebase --onto <new> <previous> lastdrop`.
4. Clean: pushes `lastdrop-sync/<tag>`, then on it runs the guard, install, `vp run typecheck`, `vp run -r test` and `vp run build:desktop`.
5. Green: moves `lastdrop` (only if nobody pushed meanwhile), tags `v<tag>-ld.<n>`, deletes the sync branch and calls `lastdrop-release.yml` (a tag pushed with the workflow token starts no workflow by itself).
6. Conflict or red: `lastdrop-sync/<tag>` stays (the upstream tag on a conflict, the rebased branch on red) with a PR into `lastdrop` carrying the log. While that branch exists the hourly job does not retry. Creating the PR needs "Allow GitHub Actions to create and approve pull requests" in the repository's Actions settings.

`lastdrop-guard.yml` runs the guard on every push and PR to `lastdrop`. A person can release by pushing a `v*-ld.*` tag, which runs `lastdrop-release.yml` directly.

### Resolving a sync

1. `git fetch origin && git fetch https://github.com/pingdotgg/t3code.git 'refs/tags/<tag>:refs/tags/<tag>'`.
2. `git switch lastdrop && git rebase --onto <tag> <previous>` (or start from `lastdrop-sync/<tag>` when checks were red).
3. For each conflict: a fork folder → keep ours; a seam → take upstream's file and re-apply the seam from its section above; `pnpm-lock.yaml` → take upstream's, then run `pnpm install --lockfile-only` at the end; anything else → it should not differ from upstream: take upstream's.
4. `node scripts/lastdrop/check-fork-paths.ts`, then the checks for the packages you touched (`vp run check:changed`) and the desktop tests.
5. `git push --force-with-lease origin lastdrop`, then push tag `v<tag>-ld.1` to release. Close the PR and delete `lastdrop-sync/<tag>`.
