# Step 8: the plugin's runner, answered by the fork

lastdrop's Claude Code plugin (`ClaudePlugin/lastdrop/hooks/register.tsx` in the standalone repo) registers each added agent as an Agent type, `lastdrop:<name>`, and answers its turns by running a runner binary with JSON-lines commands (`--agent-catalog`, `--agent-route`, `--agent-run`, `--agent-stop`, ...). Until now that binary was always the standalone app's. In a fork Claude thread, the fork answers instead: its catalog reading, its `lastdropAgents` driver (chains, fallback, the step 7 command answers), its Claude routing. The fork works without the standalone app running. Outside the fork, the plugin uses the app exactly as before.

The code is in `apps/server/src/extensions/lastdrop/runner/`. No T3 file changed and no seam was added.

## How the plugin finds the fork

- Every Claude query the fork opens carries three variables (`queryEnvironment.ts`, applied in `queryRunnerLive.ts` around the routing wrapper, so a routed query's environment keeps them):
  - `LASTDROP_RUNNER`: `<lastdrop data>/bin/lastdrop`, a short `sh` script the server writes at each start (`endpoint.ts`, `RUNNER_SCRIPT`).
  - `LASTDROP_RUNNER_URL`: `http://<loopback>:<port>/api/lastdrop/runner`, from the server's listening address.
  - `LASTDROP_RUNNER_TOKEN`: `<thread id>.<HMAC-SHA256 of it>`, keyed by a random secret held in the server's memory. A request acts as that thread only; a restart changes the secret, and every query opened after it carries a new token.
- The plugin's `runner($)` (branch `fork-runner` in the standalone repo) prefers `LASTDROP_RUNNER` while that file exists; otherwise it uses the binary beside the plugin, then `/Applications/lastdrop.app`, as before. The plugin reads the variable with `$.env.get`, as it already reads `T3CODE_THREAD_ID`. Claude Code's Bash tool inherits the variables too, so the listing's pointer (`<runner> --agents --help`) works when the model runs it.
- The variables are added to every Claude instance's queries, including Z.ai and OpenRouter. They pick no account and change no endpoint. Under vitest, and until the routes are bound, queries are unchanged.

## The runner script

`exec curl` posts each flag's request to `POST /api/lastdrop/runner/<flag without -->`, with `authorization: Bearer $LASTDROP_RUNNER_TOKEN`, and prints the answer as it streams (`--no-buffer`, `--fail-with-body`). `exec` keeps a single process, so when the plugin ends the runner (an interrupted agent), the connection closes and the route stops the run, as ending the standalone runner ends its agent. Outside a fork thread (the variables missing), the script exits 1 and says so on stderr.

- **Fallback partway**: the agents driver ends the run at a usage limit and its reactor re-sends the work as a new run of the same child thread (step 5). The runner follows the child's runs. A failed run waits 15 s for a following run, and the result is the last run's answer.
- **Delivery**: after the result, the runner reads `task_status` once, which marks the task's result delivered. T3 then doesn't also wake the parent with it.
- **Records**: `<lastdrop data>/agent-runs.json` maps each agent id to its parent thread, child thread and agent, for follow-ups after a restart. Runs in progress (for stop) are held in memory.
- **Nesting**: a child thread the runner made can't start lastdrop's agents (`error`, as the standalone app answers).

## Gaps

- **Not live through the plugin itself**: the installed plugin is the app bundle's copy, which doesn't have `fork-runner`. The plugin side is covered by its tests, and the runner side by the live runs above, which used the same environment and requests the plugin sends. A full check needs the branch's plugin installed (`--plugin-dir`, or a build of the app).
- **delegate_task texts**: with `t3Instance: false`, the plugin's T3 text says added agents can be named in delegate_task's `target.model` on the Claude instance. In `auto` mode the plugin refuses such a call and points to the Agent tool. In other modes it takes its tag path (the Claude child's own plugin then calls this runner). Background work on an added agent should use `target.providerInstanceId: "lastdropAgents"`, which T3's own listing offers. A later plugin change could take the instance id from the catalog line.
- **Claude Code's worktree**: when the engine made the subagent's worktree (`.claude/worktrees/agent-…`), the plugin passes that folder as `cwd`, and T3's delegate_task can't run a child in a given folder. The runner refuses with a clear error rather than run in the parent's checkout. A call whose isolation reaches the runner gets T3's own worktree.
- **`role` (Explore/Plan)** is not mapped: the agent runs with the parent's interaction mode.
- **Usage** (`context`, token totals) is not reported, so Claude Code counts the local conversation, as for Codex and Antigravity in the standalone app.
- **`--agent-open`**, **`--agent-warm`** and **`--agent-selftest`** do nothing useful in the fork (see the table).
- **A run outlives its server only as a T3 thread**: after a restart, the runner's in-memory registry is gone, so `--agent-stop` on a run from before answers "isn't running". The child thread still runs, and T3's Stop ends it.
