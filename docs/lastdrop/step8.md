# Step 8: the plugin's runner, answered by the fork

lastdrop's Claude Code plugin (`ClaudePlugin/lastdrop/hooks/register.tsx` in the standalone repo) registers each added agent as an Agent type, `lastdrop:<name>`, and answers its turns by running a runner binary with JSON-lines commands (`--agent-catalog`, `--agent-route`, `--agent-run`, `--agent-stop`, ...). Until now that binary was always the standalone app's. In a fork Claude thread, the fork answers instead: its catalog reading, its `lastdropAgents` driver (chains, fallback, the step 7 command answers), its Claude routing. The fork works without the standalone app running. Outside the fork, the plugin uses the app exactly as before.

The code is in `apps/server/src/extensions/lastdrop/runner/`. No T3 file changed and no seam was added.

## How the plugin finds the fork

- Every Claude query the fork opens carries three variables (`queryEnvironment.ts`, applied in `queryRunnerLive.ts` around the routing wrapper, so a routed query's environment keeps them):
  - `LASTDROP_RUNNER`: `<lastdrop data>/bin/lastdrop`, a short `sh` script the server writes at each start (`endpoint.ts`, `RUNNER_SCRIPT`).
  - `LASTDROP_RUNNER_URL`: `http://<loopback>:<port>/api/lastdrop/runner`, from the server's listening address. Only a loopback address is ever bound (`isLoopbackUrl`): a server listening on another address alone gets no runner, and the script itself refuses a URL that isn't `127.0.0.1`, `localhost` or `[::1]`, so the bearer token never leaves the machine.
  - `LASTDROP_RUNNER_TOKEN`: `<thread id>.<HMAC-SHA256 of it>`, keyed by a random secret held in the server's memory. A request acts as that thread only; a restart changes the secret, and every query opened after it carries a new token. A token holds only while its thread does: each request reads the thread's shell, and a deleted thread's token is refused (401). A read that fails doesn't refuse (the MAC already held).
- **The variables are set only while lastdrop's agents can run here**: while the "lastdrop agents" provider is off or absent, queries open without them (`runnerVariables`), and the plugin answers its Agent types through the lastdrop app as before. The check is made when a query opens; turning the provider off while a Claude session is open leaves that session's variables until it reopens (its runs then answer the provider's error).
- **Who sees the token**: the variables are in the Claude Code process's environment, so everything it starts inherits them: the Bash tool's commands, hooks, MCP servers and their children. Any of them can act as the thread through the runner (start, follow up and stop its lastdrop agents; read the catalog). That is the same reach the thread's own Agent tool has, and no more: a token names one thread, works only on this machine, and dies with the thread or the server.
- The plugin's `runner($)` (branch `fork-runner` in the standalone repo) prefers `LASTDROP_RUNNER` while that file exists; otherwise it uses the binary beside the plugin, then `/Applications/lastdrop.app`, as before. The plugin reads the variable with `$.env.get`, as it already reads `T3CODE_THREAD_ID`. Claude Code's Bash tool inherits the variables too, so the listing's pointer (`<runner> --agents --help`) works when the model runs it.
- The variables are added to every Claude instance's queries, including Z.ai and OpenRouter. They pick no account and change no endpoint. Under vitest, and until the routes are bound, queries are unchanged.

## The runner script

`exec curl` posts each flag's request to `POST /api/lastdrop/runner/<flag without -->`, with `authorization: Bearer $LASTDROP_RUNNER_TOKEN`, and prints the answer as it streams (`--no-buffer`, `--fail-with-body`). `exec` keeps a single process, so when the plugin ends the runner (an interrupted agent), the connection closes and the route stops the run, as ending the standalone runner ends its agent. Outside a fork thread (the variables missing), the script exits 1 and says so on stderr. `--agents` runs curl without `exec` and turns a refused command (HTTP 400, curl's exit 22) into exit 1, as the app's command exits.

- **Fallback partway**: the agents driver ends the run at a usage limit and its reactor re-sends the work as a new run of the same child thread (step 5), with the message id `lastdrop-fallback:<run>`. The runner follows only continuations of its own run: that message id, or T3's `usageLimitContinuationOfRunId` / `restartContinuationOfRunId`. A later run the user started in the child, or a background wake, is never followed. A failed run waits 15 s for a continuation, and the result is the last continuation's answer.
- **Delivery**: before the `result` line (the plugin ends the runner on reading it), the runner reads `task_status`, which marks the task's result delivered once T3 shows the task ended. It reads again until it does (up to 30 reads a second apart), uninterruptibly, so T3 doesn't also bring the same answer to the parent after its turn.
- **Reads that fail**: a failed read of the child while following is read again; 30 in a row let the run go. A run let go, or a finished run whose answer can't be read (also retried 30 times), is never stopped and never marked delivered: the `result` says so (`isError`), the agent keeps running in T3, and T3 brings its answer to the parent as the task's completion.
- **Ending the runner**: the plugin ending the runner stops the agent only while this runner still owns the run: not after a follow-up with the same id (a steer) took it over, and not when the child already runs something newer than the runs this runner followed.
- **Records**: `<lastdrop data>/agent-runs.json` maps each agent id to its parent thread, child thread and agent, for follow-ups after a restart. Each write reads the file again and keeps entries another server sharing the folder wrote since (`makeStoredMap`, for every lastdrop map file); a key deleted here isn't taken back. Runs in progress (for stop) are held in memory.
- **Nesting**: a thread on the `lastdropAgents` instance (its model selection or any of its runs), or one the runner made, can't start lastdrop's agents (`error`, as the standalone app answers). The check reads T3, so old children dropped past the records' 2000-entry cap still count.

## Gaps

- **Not live through the plugin itself**: the installed plugin is the app bundle's copy, which doesn't have `fork-runner`. The plugin side is covered by its tests, and the runner side by the live runs above, which used the same environment and requests the plugin sends. A full check needs the branch's plugin installed (`--plugin-dir`, or a build of the app).
- **delegate_task texts**: with `t3Instance: false`, the plugin's T3 text says added agents can be named in delegate_task's `target.model` on the Claude instance. In `auto` mode the plugin refuses such a call and points to the Agent tool. In other modes it takes its tag path (the Claude child's own plugin then calls this runner). Background work on an added agent should use `target.providerInstanceId: "lastdropAgents"`, which T3's own listing offers. A later plugin change could take the instance id from the catalog line.
- **Worktrees: T3 makes them, not Claude Code.** T3's thread launch has an `existing_worktree` strategy, but `delegateTask` (the only way into it that keeps T3's checks, receipts and wakes) accepts only `isolation: "worktree"`, and changing `OrchestratorMcpService.ts` is off limits (FORK.md). So under the fork's runner the plugin no longer moves the run into the engine's worktree: it passes the call's isolation through, T3 makes the child's worktree, and the result names it. Claude Code still makes its own worktree for the subagent (the call reaches the engine unchanged); nothing runs there, and Claude Code removes it as unchanged. A call that still arrives from another folder (an older plugin) is refused, never run in the parent's checkout.
- **Live recheck**: the review fixes are covered by tests only; the live runs above predate them.
- **`role` (Explore/Plan)** is not mapped: the agent runs with the parent's interaction mode.
- **Usage** (`context`, token totals) is not reported, so Claude Code counts the local conversation, as for Codex and Antigravity in the standalone app.
- **`--agent-open`**, **`--agent-warm`** and **`--agent-selftest`** do nothing useful in the fork (see the table).
- **A run outlives its server only as a T3 thread**: after a restart, the runner's in-memory registry is gone, so `--agent-stop` on a run from before answers "isn't running". The child thread still runs, and T3's Stop ends it.
