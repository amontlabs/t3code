## Launch

- App A was unzipped to the scratch folder and launched with `env -i HOME USER LOGNAME SHELL LANG PATH TMPDIR open -n "<app>" --env T3CODE_HOME=$S/t3home`.
- **Launch environment matters.** The first launch, started from this agent's shell, inherited its `CLAUDE_CONFIG_DIR`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, `T3CODE_THREAD_ID` and `LASTDROP_SUBAGENT`. `open -n` passes the caller's environment too. With `CLAUDE_CONFIG_DIR` set, the router rightly leaves queries alone ("… is set"). So threads ran on claude-2 with no routing line. Everything below ran on the clean launch. A user launching from the Dock or Finder gets launchd's environment, so this only affects launches from a terminal inside a Claude Code session.
- GUI automation: LCU refused, since the user had not approved "T3 Code lastdrop" for computer use, and that was not worked around. The checks drove the server with the bundled `t3` CLI (`$S/t3home/bin/t3`) and the same web client the window loads, in Playwright's bundled headless Chromium, paired through `t3 auth pairing create`. ## Bugs and gaps

Fixed on this branch: none. Each of the issues below needs more than a small change, or a T3 seam.

1. **"lastdrop agents" shows on but is off** (fresh home, or any home without `providerInstances.lastdropAgents`). The server enables an unconfigured instance only if it is `codex` or `claudeAgent` (`DEFAULT_ENABLED_DEFAULT_INSTANCES`, `packages/contracts/src/settings.ts:1580`), so a thread on it is refused: "Provider instance "lastdropAgents" is disabled for project …". The Providers card's switch falls back to the driver's default (on), so it shows on. Turning it off and on fixes it. Step 5 knew the instance needs enabling once; the new finding is that the UI says it's on. A fix needs a seam in `settings.ts` (add `lastdropAgents` to the default-enabled set) or a first-start write of the instance into the shared settings. Fork-path decision, so not done here.
2. **Update relaunch drops `T3CODE_HOME`.** A build run with its own home through the environment (as here) comes back after an update on the default `~/.t3`. There the official app's server held the ownership lock, so B's server exited with code 78 before opening the database (`server-child.log`: `code=78`), and B quit. Before that, B had already rewritten the shared `~/.t3/bin/t3` shim to point at itself (the risk FORK.md notes), and it appended to `~/.t3/userdata/logs/{server-child.log,renderer-history.ndjson}` and created `~/.t3/userdata/cli-command-first-launch`. In normal use, with the fork on `~/.t3` and nothing in its launch environment, this cannot happen. It does affect any test or dev run of a built fork on a scratch home, so a later two-version check should use a home that doesn't need the environment, or have the relaunch keep it. **The shim was left pointing at this check's scratch app**: restoring it to the official app was refused by the session's auto mode (a write into `~/.t3`). The official app rewrites it at its next start; until then it works only while the scratch app exists.
3. **`t3 thread start --wait` reports `failed` at a fallback.** When an agent's first entry hits a usage limit, `--wait` returns `status: failed` with the provider's limit text, while lastdrop keeps going on the next entry and the thread then completes. Not checked: whether a `delegate_task` parent also sees the child fail at that point. If it does, parents give up on work that is still running. Needs a look at how the agents driver ends the first run (a T3 turn failure) versus the handover.
4. **Fallback wording**: a switched-off instance is reported as "is not set up".
5. **Routing log detail**: `thread 29812447: new on claude-2 (new thread)` names the rule, not the readings that decided it (claude-2 weekly 92% vs Ultra 98%).
6. **Usage per account** (plan: "T3's Usage page must handle several Claude accounts; limits per account on hover over the usage icon"): not built. The Usage page's Limits shows one Claude block, for the account the instance last ran on. The per-account view exists only in the Claude card's Accounts section.
7. **Keychain prompt at first launch** (expected, FORK.md): the first launch waited behind the `t3code Safe Storage` prompt with only the splash showing, even with a scratch home.
